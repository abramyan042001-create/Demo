Корочки.есть — подробный учебный проект для ДЭ

Готовый локальный портал записи на курсы по присланной инструкции «Решение ДЭ Корочки есть». Python + Django + SQLite. Написанный для проекта код сопровождается русскими пояснениями к каждой непустой строке: что делает строка, откуда берутся данные и зачем действие требуется.

Начните с START_HERE.html: скачайте весь проект и откройте этот файл в браузере. Он содержит пособие и работает без сервера и интернета. В GitHub HTML показывается как исходник, поэтому для чтения его нужно скачать. Все тексты также лежат в docs/ в Markdown.

Быстрый запуск без интернета

Нужен заранее установленный Python 3.10+; для подготовки рекомендуем Python 3.12 со стандартными модулями pip, venv и ensurepip.

  1. Распакуйте полный Demo_offline.zip в обычную папку. Не запускайте изнутри ZIP.
  2. Откройте терминал в папке, в которой находятся manage.py и bootstrap.py.
  3. Выполните одну команду ниже.
  4. При первом запуске введите пароль администратора из вашего задания. Символы ввода не показываются — это нормально. Логин администратора: Admin.
  5. Откройте http://127.0.0.1:8000/ в браузере. Терминал должен оставаться открытым. Остановка — Ctrl+C.
# Создать окружение, установить локальные пакеты, подготовить БД и запустить сервер.
python bootstrap.py

В Windows, если python не найден, используйте py -3 bootstrap.py. Подробности: START_WINDOWS.md.

GitHub-копия не включает бинарные wheel-пакеты. Если скачали только её, сначала при наличии интернета выполните python bootstrap.py --prepare. Полный офлайн-архив уже содержит эти пакеты. Обычный запуск использует pip --no-index: скачивание из сети отключено.

Курсов ровно три, как в инструкции. Статусы идут по порядку: «Новая» → «Идет обучение» → «Обучение завершено». Пароли хешируются стандартными механизмами Django. Административная роль хранится в БД. Все POST-формы защищены CSRF. Автоэкранирование HTML включено. Секретный ключ автоматически создаётся на компьютере и исключён из Git; пароль администратора публично не хранится.

Структура

  • config/ — настройки Django и главная маршрутизация.
  • portal/models.py — таблицы, поля, связи, индексы, ограничения БД.
  • portal/validators.py — единые серверные регулярные выражения.
  • portal/forms.py — формы и правила проверки пользовательского ввода.
  • portal/views.py — обработчики запросов и проверка прав.
  • portal/urls.py — адреса и имена маршрутов.
  • portal/migrations/ — воспроизводимая схема БД, с пояснениями строк.
  • portal/management/commands/seed.py — создание справочника и администратора.
  • templates/ — HTML с построчными комментариями Django {# ... #}.
  • static/ — локальные CSS, JavaScript и SVG с построчными комментариями.
  • tools/ — экспорт схемы и дополнительная проверка слайдера.
  • offline_packages/ — памятка и контрольные суммы; в полном ZIP также wheel-пакеты.

Структура адаптирована к Django: это соответствует требованию полного стека и ООП; имена backend/frontend в исходной инструкции даны как пример, а не обязательный каркас.

Ограничения исходных материалов

В присланном 7z лежит только HTML-пособие, а не полный официальный комплект КОД. Упомянутых в нём фотографий, логотипов и дополнительных вариантов задания нет. Для слайдера созданы локальные SVG; замена на выданные фотографии описана в MODULE_2.md.

ER автоматически построена по фактической структуре SQLite через PRAGMA и Graphviz. Если эксперт требует именно экспорт из DBeaver/Workbench/pgAdmin, на площадке откройте свою БД в выданной программе и сохраните дополнительный экспорт; последовательность есть в пособии. Выбор SQLite тоже нужно сверить с разрешённой на площадке СУБД.

Это подготовительная работа. Разрешение использовать готовые исходники и пособие на самом экзамене определяет площадка. В день экзамена соблюдайте выданный порядок самостоятельного выполнения. История этого репозитория отражает этапы подготовки, а не прохождение экзамена.

Запуск в Windows: от скачанного архива до страницы

1. Что подготовить заранее

Установите Python, рекомендуем 3.12. Во время установки включите pip и Add Python to PATH. Нужен обычный локальный браузер. VS Code удобен для чтения кода, но портал работает и без него. Git нужен для истории изменений и отправки работы. Node.js и Graphviz не нужны для запуска портала: они используются только дополнительными инструментами проверки и экспорта.

Перед экзаменом уточните доступную версию Python, наличие Django в общей офлайн-папке, разрешённую СУБД и правила переноса материалов. Если разрешён только PostgreSQL/MySQL, нельзя просто считать этот SQLite-проект полностью соответствующим: сначала замените настройки БД, заранее подготовьте драйвер и проверьте миграции в выданной СУБД.

Проверьте Python в терминале:

# Показывает версию Python через стандартный Windows launcher.
py -3 --version
# Показывает версию pip для того же Python, а не случайной другой установки.
py -3 -m pip --version

2. Где должна быть папка проекта

Распакуйте Demo_offline.zip, например в C:\Study\Demo. В этой папке непосредственно должны находиться manage.py, bootstrap.py, README.md, config/, portal/, templates/ и offline_packages/. Если появилась дополнительная вложенная папка Demo, перейдите именно в неё.

Не открывайте проект внутри окна архиватора: относительные пути и сохранение SQLite будут работать неправильно. Не переносите готовую .venv между компьютерами: окружение содержит пути конкретной установки Python. Переносите исходники и wheel-пакеты; новое окружение создаст bootstrap.

3. Самый короткий запуск

В VS Code: «Файл → Открыть папку» и выберите Demo. Затем «Терминал → Новый терминал». В проводнике Windows можно открыть папку и в адресной строке написать powershell.

# Перейти в распакованную папку; кавычки нужны, если путь содержит пробелы.
cd C:\Study\Demo
# Установить всё из локальной папки и запустить сервер.
py -3 bootstrap.py

Первый запуск создаёт .venv, ставит четыре пакета из offline_packages, создаёт SQLite, запрашивает пароль нового администратора, проверяет настройки и включает сервер. Введите пароль, указанный в экзаменационном условии, и нажмите Enter. Ввод не отображается даже звёздочками. При повторном запуске seed не запрашивает и не сбрасывает существующий пароль.

Откройте в браузере http://127.0.0.1:8000/. Адрес 127.0.0.1 означает этот же компьютер: интернет не нужен. Оставьте терминал открытым, пока работаете с порталом. Ctrl+C останавливает сервер.

4. Ручной запуск, чтобы понимать каждый шаг

Команды ниже выполняются последовательно из папки Demo в PowerShell. Путь .venv\Scripts\python.exe явно выбирает нужный интерпретатор, поэтому активация окружения не обязательна.

# Создать изолированное окружение в папке .venv; файлы проекта не меняются.
py -3 -m venv .venv
# Установить фиксированные версии исключительно из локальных wheel-пакетов; --no-index отключает сеть.
.\.venv\Scripts\python.exe -m pip install --no-index --find-links offline_packages -r requirements-offline.txt
# Создать таблицы по сохранённым миграциям; эту команду безопасно выполнять повторно.
.\.venv\Scripts\python.exe manage.py migrate
# Добавить три курса и администратора; пароль нового аккаунта ввести по условию задания.
.\.venv\Scripts\python.exe manage.py seed
# Проверить настройки, модели и конфигурацию.
.\.venv\Scripts\python.exe manage.py check
# Запустить локальный сервер; после этой строки терминал занят до Ctrl+C.
.\.venv\Scripts\python.exe manage.py runserver

5. Git Bash

В проводнике откройте папку Demo и выберите Git Bash Here. Если такого пункта нет, откройте Git Bash отдельно и перейдите по пути:

# В Git Bash диск C записывается как /c; кавычки сохраняют пробелы в пути.

# Windows launcher доступен и из Git Bash, если установлен Python.

Для ручных команд в Git Bash можно использовать .venv/Scripts/python.exe manage.py runserver. Команда source .venv/Scripts/activate делает python из окружения доступным без полного пути, но bootstrap и явный путь работают без активации.

6. Если скачали только GitHub

На странице репозитория выберите Code → Download ZIP и распакуйте. GitHub ZIP содержит исходники, инструкции и макеты, но не бинарные wheel-пакеты. Пока интернет доступен, выполните:

# Скачать зависимости в offline_packages; это подготовительный онлайн-режим.
py -3 bootstrap.py --prepare
# После скачивания проверить обычный запуск; он устанавливает пакеты без обращения к сети.
py -3 bootstrap.py

Лучше один раз выключить интернет и убедиться, что повторный запуск работает. Не удаляйте wheel-файлы. Сам Python должен быть установлен до отключения интернета.

Как выполнить работу по пунктам и понимать результат

1. Что именно дано

Присланный файл — HTML-пособие по порталу «Корочки.есть». Оно описывает три модуля, но не заменяет выданный на площадке полный официальный вариант КОД. Мы реализовали все описанные функции, добавили учебные комментарии и инструкции для самостоятельного воспроизведения. Внешних CDN, API, Google Fonts и удалённых изображений в приложении нет.

ПА использует модуль 1, базовый уровень — 1+2, профильный — 1+2+3. В репозитории показан итог всех трёх модулей. В модуле 1 уже используется справочник Course, поскольку это сразу даёт правильную итоговую схему; необязательно сначала хранить название строкой и потом перестраивать таблицу.

Прежде чем переписывать код на экзамене, сверяйте правила варианта: разрешённую СУБД, фреймворк, названия курсов, формат телефона и даты, права на использование готовых материалов. Подготовка должна помочь воспроизвести решение, а не подменять экзаменационное выполнение.

2. Какие файлы за что отвечают

Представьте обычную бумажную запись на курс. Таблица — это журнал заявок. Модель описывает графы журнала. Форма проверяет, правильно ли человек заполнил бланк. View — сотрудник, который принимает бланк, проверяет право действия и переносит данные в журнал. Шаблон — внешний вид бланка и страницы. URL — адрес нужного окошка.

3. Подготовительный день

  1. Уточните, какой Python и какая СУБД установлены. Этот вариант рассчитан на Django 5.2 и SQLite. Переход на PostgreSQL/MySQL требует заранее установленного драйвера и другой конфигурации DATABASES.
  2. Проверьте офлайн-пакеты. В полном ZIP они уже есть. Если работаете от GitHub-копии, скачайте их заранее через python bootstrap.py --prepare.
  3. Проверьте запуск без интернета на том же компьютере и тем же Python, которым будете работать. Наличие файлов само по себе не доказывает, что всё установлено правильно.
  4. Узнайте адрес индивидуального Git-репозитория на сервере площадки. GitHub в интернете во время экзамена недоступен; используйте выданный локальный сервер.
  5. Уточните наличие DBeaver/другой программы для ER и возможность открытия SQLite. Не загружайте драйвер в момент экзамена: подготовьте его заранее разрешённым способом.
  6. Проверьте, разрешено ли переносить пособия и готовые файлы. История нашего Demo — учебная; необходимые экзаменационные коммиты делаются при выполнении экзамена.

4. Модуль 1: начало и каркас

Сразу создайте папку проекта и README, настройте Git и сделайте реальный первый коммит. Только затем начинайте ядро. В репозитории подготовки есть последовательность start/done для каждого модуля, чтобы было видно деление работы.

# Инициализировать локальную историю в текущей папке проекта; нужно только для нового проекта.
git init
# Подготовить README к включению в первый коммит.
git add README.md
# Зафиксировать начало работы над модулем.
git commit -m "module 1 start"

На новом самостоятельном проекте можно создать каркас стандартными командами Django:

# Создать конфигурационный пакет config и manage.py в текущем каталоге; точка означает текущую папку.
python -m django startproject config .
# Создать приложение предметной области portal.
python manage.py startapp portal

В уже скачанном Demo эти команды выполнять не надо: файлы существуют. Изучая с нуля, добавьте portal в INSTALLED_APPS, задайте AUTH_USER_MODEL до первого migrate и подключите portal.urls. Сначала решите, какие данные нужны, и напишите models.py.

5. Спроектировать БД

В этом проекте три предметные сущности:

  • User — учётная запись, хеш пароля, ФИО, телефон, email, флаг роли is_staff.
  • Course — уникальное название курса и флаг доступности записи.
  • Application — владелец, курс, дата начала, оплата, статус, текст отзыва и время создания.

Один User может иметь много Application. Один Course тоже может иметь много Application. Каждая отдельная Application имеет ровно одного владельца и один курс. Отзыв хранится полем заявки: здесь не требуются несколько независимых отзывов на одно прохождение обучения.

Пользовательские поля наследуются от AbstractUser. Поэтому в настоящей таблице больше колонок, чем в минимальном рисунке пособия: password, last_login, is_superuser, username, first_name, last_name, email, is_staff, is_active, date_joined, full_name, phone и id. Поле password уже предназначено для хранения хеша. Отдельный password_hash с дублированием не нужен.

Django дополнительно создаёт служебные таблицы: сессии, разрешения, группы, типы содержимого и историю миграций. Они не новые предметные сущности портала. Полная схема есть в db/schema.sql; основная ER показывает три предметные таблицы со всеми их реальными колонками.

Ограничения:

  • username уникален; дополнительный индекс LOWER(username) не позволяет обойти уникальность другим регистром.
  • В status допустимы только new/studying/completed.
  • В payment_method допустимы только cash/phone_transfer.
  • Непустой review_text возможен только при completed.
  • PROTECT не позволяет удалить пользователя или курс, пока на него ссылаются заявки.

После моделей создайте и примените миграцию:

# Сравнить описанные модели с историей и записать изменение схемы в Python-файл.
python manage.py makemigrations portal
# Выполнить ещё не применённые миграции и создать/обновить таблицы.
python manage.py migrate
# Создать три курса и нового администратора с интерактивным вводом пароля.
python manage.py seed

В готовом Demo миграция уже есть: первый запуск требует migrate, а не повторного makemigrations. Меняя модели во время самостоятельного выполнения, сохраняйте новые миграции в Git вместе с моделями.

6. ER и SQL

Откройте db/er_diagram.svg в браузере. Она построена по настоящим таблицам db.sqlite3: скрипт читает PRAGMA table_info и foreign_key_list, а Graphviz рисует связи. Поэтому схема согласована с реализацией, а не существует отдельно от неё.

В инструкции отдельно подчёркнут экспорт через программу работы с СУБД. Если эксперт требует именно такой артефакт, выполните на площадке:

  1. Откройте DBeaver и создайте соединение SQLite.
  2. Выберите фактический файл db.sqlite3 из вашего проекта. Если разрешён другой движок, создайте соединение с выданной БД.
  3. Обновите список таблиц после migrate.
  4. Выберите portal_user, portal_course и portal_application и откройте ER Diagram/диаграмму связей; название пункта зависит от установленной версии программы.
  5. Проверьте две связи: user_id → portal_user.id и course_id → portal_course.id.

В db/schema.sql нет данных пользователей и хешей. Это справочный экспорт, рабочую БД создавайте migrate, иначе история Django и вручную созданные таблицы могут разойтись.

7. Регистрация

Читайте в таком порядке: validators.py → RegistrationForm в forms.py → register_view в views.py → маршрут register → templates/portal/form.html.

При GET форма пустая. При POST Django получает строки из request.POST. Поля формы проверяют обязательность, длину и формат. ModelForm дополнительно проверяет модель. is_valid возвращает True только если ошибок нет. После этого UserCreationForm.save создаёт пользователя, используя set_password. Административные поля в форму не включены, поэтому добавление is_staff=1 в POST ничего не даёт.

clean_username проверяет занятость без учёта регистра. При двух одновременных регистрациях обе формы могут предварительно пройти проверку; окончательно уникальность обеспечивает сама БД. IntegrityError перехватывается внутри отдельной транзакции и превращается в ошибку формы.

Зачем повтор пароля: чтобы поймать опечатку до регистрации. Это дополнительное удобство; минимальное требование исходной инструкции — пароль не короче восьми символов.

8. Вход и сессия

AuthenticationForm сама проверяет логин и пароль через систему auth. После успеха login(request, user) создаёт авторизованную сессию; браузер получает cookie sessionid, а данные сессии сохраняются сервером. Пароль не записывается в cookie. Middleware на следующем запросе определяет request.user.

У Admin пять символов. Правило «минимум шесть» относится к созданию обычного логина; его нельзя механически перенести на поле входа, иначе заданный администратор не сможет авторизоваться.

Логин в этом проекте вводится с тем же регистром, с которым зарегистрирован. Проверка уникальности строже: разные регистры не дают создать второй похожий аккаунт. Например, зарегистрированный student123 входит как student123.

Гостя декоратор login_required отправляет на вход. У пользователя после входа открываются заявки; у is_staff=True — панель. Параметр next не используется, поэтому его нельзя применить для перенаправления на чужой сайт.

9. Заявка и личный список

ApplicationForm принимает только course, start_date и payment_method. Выбранный Course проверяется среди активных курсов. DateField сначала преобразует строку в настоящую дату и отвергает невозможные значения, например 31 февраля. Дополнительная проверка требует точный формат ДД.ММ.ГГГГ и запрещает прошлое. Запрет прошлой даты — разумное дополнительное правило текущей реализации; если официальный вариант требует другое, измените clean_start_date.

form.save(commit=False) создаёт объект заявки в памяти. Сервер устанавливает item.user=request.user и status=new. Только затем item.save отправляет INSERT в БД. Присланный из браузера user_id никогда не используется для назначения владельца.

В списке обязательно стоит filter(user=request.user). Нельзя сначала выбрать все заявки и спрятать чужие в HTML: сервер уже передал бы лишние данные. select_related("course") не меняет права, он только уменьшает число запросов для получения названий курсов.

10. Административные статусы

Есть две отдельные проверки роли: при открытии панели и при отправке смены статуса. Даже если обычный пользователь узнает URL обработчика, POST получит 403.

StatusForm разрешает оставить текущий статус либо перейти на один этап вперёд. new→completed сразу и completed→new запрещены. Это соответствует указанной в пособии последовательности и сохраняет правило отзыва. Смена выполняется условным UPDATE с прежним статусом: параллельный запрос не перезапишет уже обновлённое состояние.

GET-параметры status и page управляют просмотром. Paginator отдаёт по пять заявок. Ссылки страниц сохраняют фильтр. messages.success/error переживает redirect и выводится на следующей странице с role=status и aria-live.

11. Отзыв

Форма в личном списке появляется только при completed. Сервер проверяет статус повторно. Запись выбирается сразу с условием user=request.user: подмена id чужой заявки приводит к 404. Пустой текст и длина более 2000 символов отклоняются формой.

Если человек введёт HTML, Django при выводе превращает специальные символы в текст. Нельзя добавлять |safe для отзыва. Один отзыв можно отредактировать: он остаётся в той же заявке, второй независимый отзыв не создаётся.

1. Как читать построчные комментарии

В Python # начинает комментарий до конца строки. В JavaScript здесь используется //, в CSS — /* ... */, в SVG и статическом HTML — <!-- ... -->, в Django-шаблонах — {# ... #}. Комментарий не выполняет действие: он объясняет выполняемую часть слева или строку ниже.

Комментарии стоят у всех непустых строк написанного исходного кода, включая импорты и закрывающие скобки. Пустая строка служит только визуальным разделителем. Автоматически экспортированные ER, SQL и мобильные снимки — производные материалы; их читаемые первоисточники тоже снабжены пояснениями. Сторонние wheel-пакеты содержат собственный код Django и зависимостей: переписывать их внутренности не нужно.

Для изучения откройте файл целиком и сначала прочитайте текст справа от кода. Затем закройте комментарии и попробуйте произнести назначение строки самостоятельно. В VS Code Ctrl+F ищет слово по текущему файлу, Ctrl+Shift+F — по всему проекту; интернет для этого не нужен.

2. Самые первые символы Python

name = value присваивает значение переменной. name == value сравнивает значения и возвращает True или False. != означает «не равно». Один = в условии вместо == здесь является ошибкой синтаксиса.

Строки находятся в кавычках. Число 8 — число, а "8" — текстовый символ. None означает отсутствие значения. True и False — логические значения. not меняет логическое значение на противоположное, and требует выполнения обоих условий, or допускает хотя бы одно.

[] — список, например перечень приложений. {} — словарь с парами ключ:значение, например настройки БД. { "new", "studying" } без двоеточий — множество разрешённых значений. () — вызов функции или кортеж, в зависимости от контекста.

Двоеточие в конце if/for/def/class начинает блок. Отступ в четыре пробела показывает, какие строки входят в этот блок. Здесь отступ является частью синтаксиса, а не просто украшением. Уменьшение отступа завершает блок.

return сразу заканчивает функцию и отдаёт результат вызывающему коду. В view результатом должен быть HTTP-ответ: render или redirect. После return та же функция дальше не выполняется.

raise создаёт исключение: например, ValidationError сообщает форме, что значение некорректно. try/except позволяет обработать ожидаемую ошибку. Важно перехватывать конкретную ошибку, а не скрывать всё подряд. Поэтому конфликт уникальности обрабатывается как IntegrityError.

3. Импорт и модуль

Модуль — обычный Python-файл, из которого можно взять функции и классы. Пакет — папка модулей; init.py явно обозначает её как пакет. from .models import User означает: из models.py в текущем пакете взять класс User. Точка перед models указывает относительный импорт.

Импорт не копирует исходник в текущий файл: он загружает модуль и даёт доступ к его объектам. В manage.py импорт диспетчера Django выполняется после выбора DJANGO_SETTINGS_MODULE, потому что Django должен сначала знать настройки.

4. Функция, класс, объект и self

Функция — именованная последовательность действий. def login_view(request) объявляет функцию с аргументом request. Вызов login_view(request) передаёт конкретный запрос и получает ответ.

Класс описывает общий тип объектов и их поведение. User — описание пользователя, а конкретный зарегистрированный Иван — объект User. Application — описание заявки, а заявка №17 — отдельный объект Application.

Наследование записывается в скобках: class User(AbstractUser). Наш класс получает поля и методы родительского, затем добавляет ФИО и телефон. Это пример ООП. Мы не пишем собственный алгоритм хеширования: наследуем проверенный механизм.

self — ссылка на конкретный экземпляр, для которого вызван метод. В self.fields["course"] речь о поле конкретной формы. В self.instance.status — о статусе конкретной заявки, связанной с этой формой. cls в setUpTestData — ссылка на сам класс теста, а не отдельный тестовый объект.

__init__ вызывается при создании объекта. super().__init__(*args, **kwargs) сначала выполняет родительскую подготовку, чтобы у формы появились стандартные поля. *args передаёт произвольные позиционные аргументы, **kwargs — именованные. Не удаляйте super из ApplicationForm: иначе self.fields не будет подготовлен.

__str__ определяет понятное текстовое представление объекта. Благодаря Course.str список выбора показывает «Основы веб-дизайна», а не техническое «Course object (1)».

Вложенный class Meta — специальное соглашение Django: это параметры внешнего класса. У модели Meta задаёт ordering, indexes, constraints. У ModelForm Meta задаёт model и fields. Это разные настройки, хотя имя одинаковое.

5. Откуда начинается программа

Команда python manage.py runserver сначала запускает manage.py. В sys.argv находятся имя файла и слово runserver. if __name__ == "__main__" проверяет прямой запуск файла. os.environ.setdefault указывает config.settings. Затем execute_from_command_line передаёт команду Django.

Django загружает настройки, приложения, middleware и URL-маршруты, после чего запускает сервер разработки. Он остаётся работать, пока вы не нажмёте Ctrl+C. Браузер обращается к нему через 127.0.0.1:8000.

127.0.0.1 — локальный адрес, а 8000 — номер порта. Это не адрес удалённого сайта и не обращение к интернету. Если работаете с другим портом, в браузере тоже нужно указать его.

6. Полный путь одной заявки

  1. Пользователь открывает /applications/new/. Браузер отправляет GET.
  2. config.urls передаёт адрес в portal.urls.
  3. Маршрут находит new_application_view.
  4. login_required проверяет сессию. Гостя перенаправляет на вход.
  5. ApplicationForm(None) создаёт несвязанную пустую форму.
  6. render объединяет форму с HTML-шаблоном и возвращает ответ 200.
  7. Человек выбирает курс, дату и способ оплаты и нажимает кнопку.
  8. Браузер проверяет required, pattern и типы полей и отправляет POST.
  9. CSRF-middleware проверяет токен. AuthenticationMiddleware определяет request.user.
  10. View создаёт ApplicationForm(request.POST).
  11. is_valid выполняет проверки полей, clean_start_date и модели. Очищенные значения попадают в cleaned_data.
  12. save(commit=False) создаёт объект без записи в БД.
  13. View устанавливает владельца из сессии и начальный статус new.
  14. item.save выполняет INSERT с параметрами через ORM.
  15. messages запоминает текст успешного результата.
  16. redirect возвращает HTTP 302 на список.
  17. Браузер делает новый GET к /applications/.
  18. filter(user=request.user) выбирает только заявки владельца.
  19. Шаблон рисует карточки и сообщение. На этом запрос завершён.

POST/Redirect/GET предотвращает обычное повторение POST при обновлении уже открытого списка. Это не полноценная серверная идемпотентность: если намеренно отправить два отдельных валидных POST, могут появиться две заявки. Кнопка блокируется во время отправки для удобства, но не заменяет отдельный механизм защиты от намеренных дублей, который исходное пособие не требует.

7. GET, POST, request и response

GET нужен для просмотра. Его параметры находятся в URL: ?status=new&page=2. POST нужен для операций с состоянием: регистрация, вход, запись, отзыв, статус, выход. Его поля приходят в теле запроса и доступны через request.POST. Сам по себе POST не шифрует данные: шифрование при публичном размещении даёт HTTPS; здесь приложение локальное.

request.method — строка GET или POST. request.user — пользователь, установленный сервером по сессии. request.GET.get("status", "") читает параметр и использует пустую строку по умолчанию. request.POST if request.method == "POST" else None — условное выражение: выбирает данные формы или отсутствие данных.

Нельзя бездумно писать request.POST or None: пустой POST тогда превратится в несвязанную форму и может не показать обязательные ошибки. В проекте метод проверяется явно.

render(request, template, context) возвращает HTML-ответ. context — словарь переменных шаблона. redirect("applications") возвращает команду браузеру перейти на маршрут с этим именем. get_object_or_404 ищет запись и возвращает 404, если её нет. PermissionDenied даёт 403.

8. Модель и настоящая таблица

models.CharField хранит короткий текст, TextField — длинный, DateField — дату, DateTimeField — дату и время, BooleanField — логический флаг. max_length ограничивает длину на уровне форм/модели; SQLite не обеспечивает размер VARCHAR сама, поэтому серверная валидация обязательна.

null=True относится к хранению NULL в БД. blank=True разрешает пустое значение при валидации. В review_text используется blank=True и default="", поэтому отсутствующий отзыв хранится пустой строкой, без смешивания NULL и пустого текста.

default — значение для нового объекта, auto_now_add — автоматическая установка времени первой записи. У default-функции пишут timezone.now, а не timezone.now(): в первом случае Django вызовет её для каждой записи, во втором время было бы вычислено заранее один раз.

ForeignKey(User) создаёт связь и фактическую колонку user_id. item.user даёт связанный объект, item.user_id — число его id. related_name="applications" позволяет обращаться к user.applications. ForeignKey не хранит целого пользователя в каждой заявке, только его идентификатор.

PROTECT запрещает удаление родителя с дочерними записями через ORM. Это сохраняет историю. Прямые SQL-операции дополнительно подчиняются внешним ключам SQLite при включённом PRAGMA foreign_keys; Django включает их для своих соединений.

9. ORM без магии

Application.objects — менеджер, через который строится запрос. filter(...) возвращает QuerySet, то есть описание выборки. get(...) требует ровно одну запись, exists() проверяет наличие, create(...) создаёт запись. QuerySet ленивый: запрос обычно выполняется, когда данные действительно понадобились, например при переборе в шаблоне.

filter(user=request.user) примерно соответствует SQL WHERE user_id = ?. Знак вопроса здесь — параметр, а не ручная подстановка строки. ORM отделяет значения от SQL, что защищает от SQL-инъекции при обычном использовании QuerySet.

username__iexact означает нечувствительное к регистру точное сравнение. Двойное подчёркивание — синтаксис lookup Django, а не часть имени колонки. status__in=[...] означает вхождение в список значений.

select_related("user", "course") использует SQL JOIN, чтобы вместе с заявкой получить связанные данные. Без него каждая карточка могла бы дополнительно запрашивать владельца и курс. Это ускорение, оно не заменяет filter владельца и не проверяет роль.

update(...) сразу выполняет SQL UPDATE, не вызывает save и полную валидацию модели. В status_view перед update уже прошла StatusForm; условие по старому статусу защищает от перезаписи изменившегося состояния. В тестах update используется намеренно для проверки ограничений БД.

10. Зачем миграции и индексы

Модель — текущее желаемое описание. Миграция — сохранённый шаг изменения структуры. makemigrations создаёт файл шага; migrate применяет шаги к конкретной БД. Поэтому изменение models.py само по себе не меняет SQLite.

Нельзя коммитить только изменённую модель и забыть миграцию: на другом компьютере структура не воспроизведётся. Команда makemigrations --check --dry-run проверяет именно это несоответствие, не изменяя файлов.

Индекс — дополнительная структура для ускоренного поиска. В приложении индекс user+created_at помогает списку пользователя, индекс status — фильтру админа. Индексы требуют места и замедляют запись, поэтому не нужно добавлять их на каждое поле без причины. Первичный ключ и unique обычно уже получают подходящие индексы.

11. Серверная и браузерная валидация

HTML required, minlength, maxlength, pattern и type=email помогают человеку сразу исправить ошибку. Их можно обойти отключением JavaScript, изменением HTML в DevTools или отправкой HTTP-запроса вручную. Поэтому сервер проверяет всё независимо.

Форма принимает только разрешённые поля Meta.fields. Данные POST — недоверенный текст. cleaned_data содержит уже проверенные значения, иногда другого типа: id курса становится объектом Course, строка даты — datetime.date. Нельзя обращаться к cleaned_data до is_valid и считать сырые request.POST готовыми к записи.

ModelForm.is_valid дополнительно проверяет модель, но прямой model.save сам по себе не вызывает full_clean. Поэтому критические ограничения статуса, оплаты и отзыва продублированы на уровне БД. Формы нужны для понятных сообщений, ограничения БД — для целостности.

12. Регулярные выражения по частям

В validators.py логин: \A[A-Za-z0-9]{6,50}\Z.

  • \A — начало всей строки.
  • [A-Za-z0-9] — один латинский символ любого регистра или цифра ASCII.
  • {6,50} — повторить от 6 до 50 раз.
  • \Z — конец всей строки.

Телефон: \A8\([0-9]{3}\)[0-9]{3}-[0-9]{2}-[0-9]{2}\Z.

  • После начала обязателен символ 8.
  • \( и \) — настоящие скобки; без обратной косой черты скобки задавали бы группу.
  • [0-9]{3} — ровно три цифры.
  • Дефисы вне квадратных скобок являются обычными символами.
  • В результате подходит 8(999)123-45-67, а +79991234567 не подходит.

ФИО: первая группа букв кириллицы, затем ноль или больше повторений «один пробел и ещё слово». Ё/ё указаны отдельно, потому что диапазон А–Я их не включает. Дефисы в текущем правиле не разрешены: это следует выбранному в пособии формату. Если официальный вариант допускает двойные фамилии, правило нужно изменить.

Префикс r перед строкой означает raw string: обратные косые черты передаются регулярному выражению без лишнего экранирования Python. Для даты регулярка проверяет только расположение цифр и точек, а существование календарной даты проверяет DateField. Одной регуляркой нельзя надёжно заменить календарную проверку.

13. Хеширование, сессия, роль и CSRF

Хеширование пароля — одностороннее вычисление для последующего сравнения. set_password добавляет случайную соль и записывает строку с алгоритмом и параметрами. check_password проверяет введённый текст с учётом этих параметров. Два пользователя с одинаковыми паролями обычно получают разные строки хеша из-за разной соли.

Сессия отвечает на вопрос «кто уже вошёл». Роль отвечает на вопрос «что этому пользователю разрешено». is_staff — флаг в БД, которым пользуется наш административный обработчик. Скрытие ссылки в шаблоне не проверяет права: настоящая проверка находится во view.

CSRF-токен позволяет серверу отличать отправку своей формы от поддельной отправки с постороннего сайта. CsrfViewMiddleware проверяет его до view, а {% csrf_token %} добавляет скрытое поле в HTML. CSRF не заменяет проверку логина, роли, владельца и значений формы.

Локальный SECRET_KEY создаётся случайно и хранится в .local_secret. Он не пароль Admin и не хеш пользовательского пароля. Его нельзя коммитить. Удаление или смена ключа может сделать старые подписанные значения и сессии непригодными. Для учебного локального запуска достаточно текущей конфигурации; публичное развёртывание потребовало бы отдельной настройки, которую это задание не запрашивает.

14. Шаблоны Django

{% extends "base.html" %} наследует общий каркас. block content отмечает место, куда дочерняя страница вставляет свои элементы. include вставляет общий фрагмент, здесь слайдер.

{{ item.course.title }} выводит значение. {% if ... %} выбирает ветку. {% for item in items %} перебирает список. {% empty %} внутри for срабатывает при пустом списке. {% url 'review' item.pk %} строит URL по имени, а не склеивает путь вручную.

Фильтр date:"d.m.Y" форматирует дату для человека. get_status_display берёт русскую подпись из choices. striptags убирает HTML из подсказки. urlencode безопасно кодирует значение параметра URL.

Автоэкранирование включено: символ < из пользовательского текста становится &lt;. Оно защищает от интерпретации текста как HTML. В проекте нет |safe для отзывов и сообщений пользователя.

Поля форм выводятся через {{ field }}. Django сам создаёт id, name, type и текущее значение. field.errors выводит ошибки конкретного поля, form.non_field_errors — ошибки всей формы. label for связан с id поля, поэтому клик по подписи переводит фокус в нужный input.

15. CSS: как получается адаптив

display:grid создаёт сетку. grid-template-columns:1fr 1fr делит доступную ширину на две равные части. gap задаёт расстояние между колонками. minmax(0,1fr) разрешает колонке сжиматься, даже если внутри длинный текст.

box-sizing:border-box включает padding и border в заданную ширину. Без этого input width:100% плюс внутренние отступы мог бы оказаться шире карточки. overflow-wrap:anywhere разрешает перенос длинного email и названия.

@media(max-width:760px) применяется по ширине окна. На телефоне сетка становится одноколоночной, а меню переносится. Макеты mobile/ дополнительно принудительно применяют эти правила, чтобы оставаться холстом 390 px даже в большом окне компьютера.

CSS-переменные --teal и --ink задаются в :root. var(--teal) подставляет значение. Так цвет кнопок и ссылок можно изменить в одном месте. :focus-visible рисует заметную рамку для клавиатурной навигации. prefers-reduced-motion отключает анимации по настройке пользователя.

16. JavaScript: почему слайдер зациклен

Массив из четырёх кадров имеет индексы 0,1,2,3. Чтобы показать предыдущий с нуля, нужно получить 3, а не -1. Поэтому используется (nextIndex + slides.length) % slides.length. Для следующего с тройки получаем (4+4)%4=0. Остаток от деления замыкает цикл.

const запрещает переназначить ссылку переменной, let допускает изменение. index меняется, поэтому let. slides остаётся тем же массивом, поэтому const. Стрелочная функция () => show(index+1) передаёт действие, которое выполнится позднее при событии.

classList.toggle("active", active) добавляет или снимает класс по логическому условию. CSS делает активный кадр непрозрачным. setInterval получает функцию и 3000 миллисекунд. clearInterval останавливает повторение. Перед запуском нового таймера старый удаляется, иначе карусель могла бы неожиданно ускоряться.

Индикатор формы появляется при submit после стандартной валидации браузера. Повторная кнопка отключается. На pageshow она включается обратно, потому что браузер может вернуть старую страницу из кэша кнопкой «Назад». Основная логика заявки работает на сервере и не зависит от JavaScript.

17. Тесты и их границы

TestCase использует отдельную тестовую БД и откатывает данные между тестами. Client вызывает обработчики Django без настоящего браузера. Проверяются серверные ответы, права и фактические записи. Это не визуальная проверка CSS.

Слайдер проверяется отдельным Node-скриптом с минимальной моделью DOM: переходы, активный кадр, aria-hidden, таймер, пауза и отправка формы. Такой тест тоже не доказывает, что в браузере правильно отрисовались отступы.

В этой среде настоящий Chromium не стартовал из-за системного ограничения создания Unix-сокета. Поэтому на своём компьютере выполните ручную визуальную проверку пяти страниц и размера 390×844 по CHECKLIST. Не заменяйте это утверждением «все браузеры проверены».

Что могут спросить на защите

Что вы разработали?

Полноценный локальный портал записи на онлайн-курсы. Пользователь регистрируется, входит, создаёт заявку, видит свои заявки и оставляет отзыв после завершения обучения. Администратор видит все заявки и переводит их по статусам. Есть сервер, интерфейс, база данных и классы моделей/форм.

Почему выбран Django?

Он даёт готовые механизмы маршрутизации, форм, ORM, сессий, проверки паролей и CSRF. Это позволяет сосредоточиться на логике задания и не писать свою систему авторизации. Все используемые библиотеки подготовлены локально. На реальной площадке выбор нужно сверить с установленными средствами.

Где здесь ООП?

User наследуется от AbstractUser, Course и Application — от models.Model, формы — от UserCreationForm/AuthenticationForm/ModelForm, собственные команды — от BaseCommand. Экземпляр Application представляет конкретную заявку. Поля и методы объединены в классах по ответственности.

Чем модель отличается от таблицы?

Модель — Python-класс с описанием полей, связей и правил. Таблица — фактическая структура в СУБД. Django переводит описание в операции миграций; migrate применяет их к БД. После изменения models.py таблица сама по себе не изменяется.

Чем makemigrations отличается от migrate?

makemigrations создаёт файл изменения схемы. migrate выполняет ещё не применённые изменения в конкретной БД. Файл миграции переносится вместе с исходниками, а локальная SQLite создаётся при запуске.

Что означают PK и FK?

PK — первичный ключ, уникальный идентификатор строки. FK — внешний ключ, ссылка на первичный ключ другой таблицы. user_id в заявке ссылается на пользователя, course_id — на курс. Это обеспечивает связи один-ко-многим и целостность данных.

Почему курс вынесен в отдельную таблицу?

Название не повторяется текстом во всех заявках. Выбор ограничен справочником, курс можно закрыть для новых записей, не удаляя историю. В заявке хранится course_id, а название получается через связь.

Где хранится роль администратора?

В поле is_staff таблицы portal_user. Она назначается серверной командой seed, а не регистрационной формой. Открытие панели и изменение статуса независимо проверяют request.user.is_staff.

Почему Admin короче шести символов и всё равно входит?

Это специальный логин из задания. Ограничение от шести символов применяется к регистрации обычных пользователей. Вход проверяет существующую учётную запись, поэтому не повторяет этот минимум. Seed создаёт специального администратора явно.

Где пароль администратора?

Он задаётся владельцем при первом запуске seed по условию задания. В публичном репозитории его нет. В БД хранится хеш, созданный set_password. Повторный seed не сбрасывает существующий пароль.

Чем хеширование отличается от шифрования?

Шифрование рассчитано на обратное восстановление при наличии ключа. Хеш пароля используется для проверки и не требует восстановления исходного пароля. Django сохраняет параметры алгоритма и соль и сравнивает результат при входе.

Что хранится в cookie?

Идентификатор серверной сессии, а не пароль. SessionMiddleware находит сессию, AuthenticationMiddleware определяет пользователя и создаёт request.user. HttpOnly ограничивает чтение cookie из JavaScript.

Зачем серверная валидация, если браузер уже проверил поля?

Браузерные проверки можно обойти. Сервер обязан самостоятельно проверить формат, длину, выбранный курс, дату и разрешённые действия. Формы дают понятные ошибки, ограничения БД сохраняют критическую целостность.

Как защищены чужие заявки?

Личный список выбирает Application с filter(user=request.user). Отзыв ищет заявку только среди записей того же владельца. Подстановка чужого id приводит к 404. Нельзя просто скрыть чужую карточку стилями и считать данные защищёнными.

Что защищает от SQL-инъекции?

Обычные QuerySet ORM передают значения параметрами отдельно от SQL. В views нет ручной конкатенации пользовательского ввода с SQL. Фиксированные PRAGMA в инструменте экспорта читают заранее известные имена таблиц, не данные браузера.

Что защищает от XSS?

Автоэкранирование Django-шаблонов. Отзыв выводится как текст, даже если содержит <script>. Для пользовательского текста не применяется |safe, а в JavaScript для счётчика используется textContent.

Что защищает от CSRF?

CsrfViewMiddleware и скрытый csrf_token в каждой изменяющей POST-форме. Сервер отклоняет запрос без согласованного токена. Защита от CSRF дополняет проверку авторизации и роли, не заменяя их.

Почему выход через POST?

Выход изменяет состояние сессии. GET предназначен для просмотра и может запускаться переходами, предпросмотром или внешней ссылкой. POST с CSRF-токеном требует корректной формы приложения.

Почему form.save(commit=False)?

Чтобы получить объект в памяти до INSERT. Владелец ещё не пришёл из формы — его назначает сервер из request.user. После установки владельца и начального статуса можно вызвать item.save.

Почему статус не входит в форму новой заявки?

Пользователь не имеет права сам назначать completed. Поле намеренно исключено из Meta.fields, сервер присваивает new независимо от дополнительных POST-полей.

Какие переходы статуса разрешены?

Новая → Идет обучение → Обучение завершено, либо сохранение текущего статуса. Шаг назад и пропуск промежуточного этапа запрещены в StatusForm. Условный UPDATE по прежнему статусу не затирает параллельное обновление.

Когда можно оставить отзыв?

Только для собственной завершённой заявки. Это проверяется в интерфейсе, во view и ограничением БД для непустого review_text. Максимальная длина формы — 2000 символов. Существующий отзыв можно отредактировать.

Что делает select_related?

Получает связанные объекты в одном SQL-запросе через JOIN. Например, список заявок сразу включает курс и владельца, поэтому шаблон не запускает отдельные запросы для каждой карточки. Это оптимизация запросов, а не проверка прав.

Как устроены фильтр и страницы?

status и page берутся из GET. Допустимый status используется в фильтре ORM, затем Paginator делит результат по пять записей. Ссылка следующей страницы сохраняет выбранный статус. Неизвестный фильтр сбрасывается безопасно.

Почему после POST перенаправление?

При обновлении итоговой страницы браузер повторит GET списка, а не предыдущую отправку формы. Это обычный шаблон POST/Redirect/GET. Две намеренно повторённые отдельные отправки всё ещё могут создать две заявки: абсолютная идемпотентность требует отдельного решения.

Как работает слайдер?

В HTML четыре одинаковых по размеру изображения. JS хранит индекс, меняет active и aria-hidden. Остаток от деления замыкает цикл. setInterval с 3000 переключает раз в три секунды. Стрелки и клавиши делают шаг вручную. Наведение, фокус, скрытая вкладка и reduced-motion ставят автосмену на паузу.

Почему SVG, а не фото из приложения?

В присланном архиве нет самих медиа, только ссылки на их предполагаемое расположение. Для подготовки созданы собственные локальные иллюстрации. На площадке их следует заменить выданными фотографиями и логотипами, если это требуется официальным комплектом.

Где мобильная версия?

Рабочие страницы используют CSS media query до 760 px. Отдельно есть пять HTML-макетов mobile/ с холстом 390×844. Макеты статические и не записывают данные, рабочие формы действуют через локальный сервер.

Почему у регистрации высота больше 844?

844 px — минимальная высота холста и размер целевого окна. Все обязательные поля должны быть доступны, поэтому длинная форма прокручивается вертикально. Жёсткое ограничение высоты со скрытием содержимого сделало бы часть формы недоступной.

Что будет без JavaScript?

Регистрация, вход, заявки, отзывы, фильтр и смена статуса продолжат работать обычными HTML-формами. Слайдер останется на первом кадре, а визуальный индикатор отправки не появится. Основные проверки выполняются сервером.

Как доказать офлайн-работу?

Установить проект в чистое окружение из offline_packages с pip --no-index, подготовить БД и пройти сценарий без внешних сервисов. В коде нет CDN и сетевых API. Python и wheel-файлы должны быть подготовлены до отключения интернета.

Что показывать в Git?

Реальные коммиты начала и завершения каждого модуля, исходники, миграции, ER, макеты и инструкции. Не добавлять .venv, локальную БД, сессии и .local_secret. На экзамене отправка идёт на разрешённый сервер площадки, а не обязательно на GitHub.

Что ещё осталось проверить на площадке?

Разрешённую СУБД, точный официальный вариант, выданные медиа и требуемый формат ER. Дополнительно визуально проверить все пять страниц на 390×844 и широком экране, поскольку в среде подготовки Chromium не смог запуститься. Пройденные серверные и JS-проверки перечислены в VERIFICATION.md.

Схема включает нормализованный справочник курсов, внешние ключи, индексы, уникальность логина без учёта регистра и CHECK статуса/оплаты/связи отзыва с завершением. SQL и ER получены из фактической SQLite.

Реальный интерфейс содержит мобильные media queries, единые компоненты, hover, появление карточек, плавную смену кадра, сообщения после действий и индикатор отправки. Настройка reduced-motion учитывается. Страницы работают обычными серверными формами без обязательного JavaScript.

Код разделён на модели, формы, обработчики и шаблоны. Каждая непустая строка написанного исходника пояснена по просьбе пользователя; это намеренно более подробно, чем рекомендация кратких комментариев в исходном пособии.

19 серверных тестов и отдельная проверка JavaScript пройдены. Полная визуальная проверка браузером в среде подготовки заблокирована системным ограничением; сценарий ручной проверки явно выделен в CHECKLIST.md. Офлайн-установка проверяется в чистом окружении из фиксированных локальных wheel-пакетов.

Подробный план самостоятельного воспроизведения, вопросы для защиты и запуск в Windows находятся в docs/ и START_HERE.html. Сторонние бинарные зависимости поставляются в отдельном полном офлайн-архиве; исходники проекта — в GitHub.
