# Как читать код: подробный разбор простыми словами

## 1. Как читать построчные комментарии

В Python `#` начинает комментарий до конца строки. В JavaScript здесь используется `//`, в CSS — `/* ... */`, в SVG и статическом HTML — `<!-- ... -->`, в Django-шаблонах — `{# ... #}`. Комментарий не выполняет действие: он объясняет выполняемую часть слева или строку ниже.

Комментарии стоят у всех непустых строк написанного исходного кода, включая импорты и закрывающие скобки. Пустая строка служит только визуальным разделителем. Автоматически экспортированные ER, SQL и мобильные снимки — производные материалы; их читаемые первоисточники тоже снабжены пояснениями. Сторонние wheel-пакеты содержат собственный код Django и зависимостей: переписывать их внутренности не нужно.

Для изучения откройте файл целиком и сначала прочитайте текст справа от кода. Затем закройте комментарии и попробуйте произнести назначение строки самостоятельно. В VS Code Ctrl+F ищет слово по текущему файлу, Ctrl+Shift+F — по всему проекту; интернет для этого не нужен.

## 2. Самые первые символы Python

`name = value` присваивает значение переменной. `name == value` сравнивает значения и возвращает True или False. `!=` означает «не равно». Один `=` в условии вместо `==` здесь является ошибкой синтаксиса.

Строки находятся в кавычках. Число `8` — число, а `"8"` — текстовый символ. `None` означает отсутствие значения. `True` и `False` — логические значения. `not` меняет логическое значение на противоположное, `and` требует выполнения обоих условий, `or` допускает хотя бы одно.

`[]` — список, например перечень приложений. `{}` — словарь с парами ключ:значение, например настройки БД. `{ "new", "studying" }` без двоеточий — множество разрешённых значений. `()` — вызов функции или кортеж, в зависимости от контекста.

Двоеточие в конце if/for/def/class начинает блок. Отступ в четыре пробела показывает, какие строки входят в этот блок. Здесь отступ является частью синтаксиса, а не просто украшением. Уменьшение отступа завершает блок.

`return` сразу заканчивает функцию и отдаёт результат вызывающему коду. В view результатом должен быть HTTP-ответ: render или redirect. После return та же функция дальше не выполняется.

`raise` создаёт исключение: например, ValidationError сообщает форме, что значение некорректно. `try/except` позволяет обработать ожидаемую ошибку. Важно перехватывать конкретную ошибку, а не скрывать всё подряд. Поэтому конфликт уникальности обрабатывается как IntegrityError.

## 3. Импорт и модуль

Модуль — обычный Python-файл, из которого можно взять функции и классы. Пакет — папка модулей; __init__.py явно обозначает её как пакет. `from .models import User` означает: из models.py в текущем пакете взять класс User. Точка перед models указывает относительный импорт.

Импорт не копирует исходник в текущий файл: он загружает модуль и даёт доступ к его объектам. В manage.py импорт диспетчера Django выполняется после выбора DJANGO_SETTINGS_MODULE, потому что Django должен сначала знать настройки.

## 4. Функция, класс, объект и self

Функция — именованная последовательность действий. `def login_view(request)` объявляет функцию с аргументом request. Вызов `login_view(request)` передаёт конкретный запрос и получает ответ.

Класс описывает общий тип объектов и их поведение. User — описание пользователя, а конкретный зарегистрированный Иван — объект User. Application — описание заявки, а заявка №17 — отдельный объект Application.

Наследование записывается в скобках: `class User(AbstractUser)`. Наш класс получает поля и методы родительского, затем добавляет ФИО и телефон. Это пример ООП. Мы не пишем собственный алгоритм хеширования: наследуем проверенный механизм.

`self` — ссылка на конкретный экземпляр, для которого вызван метод. В `self.fields["course"]` речь о поле конкретной формы. В `self.instance.status` — о статусе конкретной заявки, связанной с этой формой. `cls` в setUpTestData — ссылка на сам класс теста, а не отдельный тестовый объект.

`__init__` вызывается при создании объекта. `super().__init__(*args, **kwargs)` сначала выполняет родительскую подготовку, чтобы у формы появились стандартные поля. `*args` передаёт произвольные позиционные аргументы, `**kwargs` — именованные. Не удаляйте super из ApplicationForm: иначе self.fields не будет подготовлен.

`__str__` определяет понятное текстовое представление объекта. Благодаря Course.__str__ список выбора показывает «Основы веб-дизайна», а не техническое «Course object (1)».

Вложенный `class Meta` — специальное соглашение Django: это параметры внешнего класса. У модели Meta задаёт ordering, indexes, constraints. У ModelForm Meta задаёт model и fields. Это разные настройки, хотя имя одинаковое.

## 5. Откуда начинается программа

Команда `python manage.py runserver` сначала запускает manage.py. В sys.argv находятся имя файла и слово runserver. `if __name__ == "__main__"` проверяет прямой запуск файла. os.environ.setdefault указывает config.settings. Затем execute_from_command_line передаёт команду Django.

Django загружает настройки, приложения, middleware и URL-маршруты, после чего запускает сервер разработки. Он остаётся работать, пока вы не нажмёте Ctrl+C. Браузер обращается к нему через 127.0.0.1:8000.

`127.0.0.1` — локальный адрес, а `8000` — номер порта. Это не адрес удалённого сайта и не обращение к интернету. Если работаете с другим портом, в браузере тоже нужно указать его.

## 6. Полный путь одной заявки

1. Пользователь открывает `/applications/new/`. Браузер отправляет GET.
2. config.urls передаёт адрес в portal.urls.
3. Маршрут находит new_application_view.
4. login_required проверяет сессию. Гостя перенаправляет на вход.
5. ApplicationForm(None) создаёт несвязанную пустую форму.
6. render объединяет форму с HTML-шаблоном и возвращает ответ 200.
7. Человек выбирает курс, дату и способ оплаты и нажимает кнопку.
8. Браузер проверяет required, pattern и типы полей и отправляет POST.
9. CSRF-middleware проверяет токен. AuthenticationMiddleware определяет request.user.
10. View создаёт ApplicationForm(request.POST).
11. is_valid выполняет проверки полей, clean_start_date и модели. Очищенные значения попадают в cleaned_data.
12. save(commit=False) создаёт объект без записи в БД.
13. View устанавливает владельца из сессии и начальный статус new.
14. item.save выполняет INSERT с параметрами через ORM.
15. messages запоминает текст успешного результата.
16. redirect возвращает HTTP 302 на список.
17. Браузер делает новый GET к /applications/.
18. filter(user=request.user) выбирает только заявки владельца.
19. Шаблон рисует карточки и сообщение. На этом запрос завершён.

POST/Redirect/GET предотвращает обычное повторение POST при обновлении уже открытого списка. Это не полноценная серверная идемпотентность: если намеренно отправить два отдельных валидных POST, могут появиться две заявки. Кнопка блокируется во время отправки для удобства, но не заменяет отдельный механизм защиты от намеренных дублей, который исходное пособие не требует.

## 7. GET, POST, request и response

GET нужен для просмотра. Его параметры находятся в URL: `?status=new&page=2`. POST нужен для операций с состоянием: регистрация, вход, запись, отзыв, статус, выход. Его поля приходят в теле запроса и доступны через request.POST. Сам по себе POST не шифрует данные: шифрование при публичном размещении даёт HTTPS; здесь приложение локальное.

`request.method` — строка GET или POST. `request.user` — пользователь, установленный сервером по сессии. `request.GET.get("status", "")` читает параметр и использует пустую строку по умолчанию. `request.POST if request.method == "POST" else None` — условное выражение: выбирает данные формы или отсутствие данных.

Нельзя бездумно писать `request.POST or None`: пустой POST тогда превратится в несвязанную форму и может не показать обязательные ошибки. В проекте метод проверяется явно.

`render(request, template, context)` возвращает HTML-ответ. context — словарь переменных шаблона. `redirect("applications")` возвращает команду браузеру перейти на маршрут с этим именем. `get_object_or_404` ищет запись и возвращает 404, если её нет. PermissionDenied даёт 403.

| Код HTTP | Значение в проекте |
| --- | --- |
| 200 | Страница успешно показана; ошибки заполнения также могут показываться на странице 200 |
| 302 | Перенаправление после действия или на вход |
| 400 | Неверный текст отзыва показан в форме для исправления |
| 403 | Нет роли/неподходящий статус/неверный CSRF |
| 404 | Запись не найдена среди доступных пользователю |
| 405 | Для этого обработчика запрещён данный HTTP-метод |
| 500 | Непредвиденная серверная ошибка; это не ожидаемая реакция на обычный неверный ввод |

## 8. Модель и настоящая таблица

`models.CharField` хранит короткий текст, `TextField` — длинный, `DateField` — дату, `DateTimeField` — дату и время, `BooleanField` — логический флаг. `max_length` ограничивает длину на уровне форм/модели; SQLite не обеспечивает размер VARCHAR сама, поэтому серверная валидация обязательна.

`null=True` относится к хранению NULL в БД. `blank=True` разрешает пустое значение при валидации. В review_text используется blank=True и default="", поэтому отсутствующий отзыв хранится пустой строкой, без смешивания NULL и пустого текста.

`default` — значение для нового объекта, `auto_now_add` — автоматическая установка времени первой записи. У default-функции пишут `timezone.now`, а не `timezone.now()`: в первом случае Django вызовет её для каждой записи, во втором время было бы вычислено заранее один раз.

`ForeignKey(User)` создаёт связь и фактическую колонку user_id. `item.user` даёт связанный объект, `item.user_id` — число его id. related_name="applications" позволяет обращаться к user.applications. ForeignKey не хранит целого пользователя в каждой заявке, только его идентификатор.

PROTECT запрещает удаление родителя с дочерними записями через ORM. Это сохраняет историю. Прямые SQL-операции дополнительно подчиняются внешним ключам SQLite при включённом PRAGMA foreign_keys; Django включает их для своих соединений.

## 9. ORM без магии

`Application.objects` — менеджер, через который строится запрос. `filter(...)` возвращает QuerySet, то есть описание выборки. `get(...)` требует ровно одну запись, `exists()` проверяет наличие, `create(...)` создаёт запись. QuerySet ленивый: запрос обычно выполняется, когда данные действительно понадобились, например при переборе в шаблоне.

`filter(user=request.user)` примерно соответствует SQL `WHERE user_id = ?`. Знак вопроса здесь — параметр, а не ручная подстановка строки. ORM отделяет значения от SQL, что защищает от SQL-инъекции при обычном использовании QuerySet.

`username__iexact` означает нечувствительное к регистру точное сравнение. Двойное подчёркивание — синтаксис lookup Django, а не часть имени колонки. `status__in=[...]` означает вхождение в список значений.

`select_related("user", "course")` использует SQL JOIN, чтобы вместе с заявкой получить связанные данные. Без него каждая карточка могла бы дополнительно запрашивать владельца и курс. Это ускорение, оно не заменяет filter владельца и не проверяет роль.

`update(...)` сразу выполняет SQL UPDATE, не вызывает save и полную валидацию модели. В status_view перед update уже прошла StatusForm; условие по старому статусу защищает от перезаписи изменившегося состояния. В тестах update используется намеренно для проверки ограничений БД.

## 10. Зачем миграции и индексы

Модель — текущее желаемое описание. Миграция — сохранённый шаг изменения структуры. makemigrations создаёт файл шага; migrate применяет шаги к конкретной БД. Поэтому изменение models.py само по себе не меняет SQLite.

Нельзя коммитить только изменённую модель и забыть миграцию: на другом компьютере структура не воспроизведётся. Команда makemigrations --check --dry-run проверяет именно это несоответствие, не изменяя файлов.

Индекс — дополнительная структура для ускоренного поиска. В приложении индекс user+created_at помогает списку пользователя, индекс status — фильтру админа. Индексы требуют места и замедляют запись, поэтому не нужно добавлять их на каждое поле без причины. Первичный ключ и unique обычно уже получают подходящие индексы.

## 11. Серверная и браузерная валидация

HTML required, minlength, maxlength, pattern и type=email помогают человеку сразу исправить ошибку. Их можно обойти отключением JavaScript, изменением HTML в DevTools или отправкой HTTP-запроса вручную. Поэтому сервер проверяет всё независимо.

Форма принимает только разрешённые поля Meta.fields. Данные POST — недоверенный текст. cleaned_data содержит уже проверенные значения, иногда другого типа: id курса становится объектом Course, строка даты — datetime.date. Нельзя обращаться к cleaned_data до is_valid и считать сырые request.POST готовыми к записи.

ModelForm.is_valid дополнительно проверяет модель, но прямой model.save сам по себе не вызывает full_clean. Поэтому критические ограничения статуса, оплаты и отзыва продублированы на уровне БД. Формы нужны для понятных сообщений, ограничения БД — для целостности.

## 12. Регулярные выражения по частям

В validators.py логин: `\A[A-Za-z0-9]{6,50}\Z`.

- `\A` — начало всей строки.
- `[A-Za-z0-9]` — один латинский символ любого регистра или цифра ASCII.
- `{6,50}` — повторить от 6 до 50 раз.
- `\Z` — конец всей строки.

Телефон: `\A8\([0-9]{3}\)[0-9]{3}-[0-9]{2}-[0-9]{2}\Z`.

- После начала обязателен символ 8.
- `\(` и `\)` — настоящие скобки; без обратной косой черты скобки задавали бы группу.
- `[0-9]{3}` — ровно три цифры.
- Дефисы вне квадратных скобок являются обычными символами.
- В результате подходит `8(999)123-45-67`, а `+79991234567` не подходит.

ФИО: первая группа букв кириллицы, затем ноль или больше повторений «один пробел и ещё слово». Ё/ё указаны отдельно, потому что диапазон А–Я их не включает. Дефисы в текущем правиле не разрешены: это следует выбранному в пособии формату. Если официальный вариант допускает двойные фамилии, правило нужно изменить.

Префикс r перед строкой означает raw string: обратные косые черты передаются регулярному выражению без лишнего экранирования Python. Для даты регулярка проверяет только расположение цифр и точек, а существование календарной даты проверяет DateField. Одной регуляркой нельзя надёжно заменить календарную проверку.

## 13. Хеширование, сессия, роль и CSRF

Хеширование пароля — одностороннее вычисление для последующего сравнения. set_password добавляет случайную соль и записывает строку с алгоритмом и параметрами. check_password проверяет введённый текст с учётом этих параметров. Два пользователя с одинаковыми паролями обычно получают разные строки хеша из-за разной соли.

Сессия отвечает на вопрос «кто уже вошёл». Роль отвечает на вопрос «что этому пользователю разрешено». is_staff — флаг в БД, которым пользуется наш административный обработчик. Скрытие ссылки в шаблоне не проверяет права: настоящая проверка находится во view.

CSRF-токен позволяет серверу отличать отправку своей формы от поддельной отправки с постороннего сайта. CsrfViewMiddleware проверяет его до view, а `{% csrf_token %}` добавляет скрытое поле в HTML. CSRF не заменяет проверку логина, роли, владельца и значений формы.

Локальный SECRET_KEY создаётся случайно и хранится в .local_secret. Он не пароль Admin и не хеш пользовательского пароля. Его нельзя коммитить. Удаление или смена ключа может сделать старые подписанные значения и сессии непригодными. Для учебного локального запуска достаточно текущей конфигурации; публичное развёртывание потребовало бы отдельной настройки, которую это задание не запрашивает.

## 14. Шаблоны Django

`{% extends "base.html" %}` наследует общий каркас. block content отмечает место, куда дочерняя страница вставляет свои элементы. include вставляет общий фрагмент, здесь слайдер.

`{{ item.course.title }}` выводит значение. `{% if ... %}` выбирает ветку. `{% for item in items %}` перебирает список. `{% empty %}` внутри for срабатывает при пустом списке. `{% url 'review' item.pk %}` строит URL по имени, а не склеивает путь вручную.

Фильтр `date:"d.m.Y"` форматирует дату для человека. `get_status_display` берёт русскую подпись из choices. `striptags` убирает HTML из подсказки. `urlencode` безопасно кодирует значение параметра URL.

Автоэкранирование включено: символ `<` из пользовательского текста становится `&lt;`. Оно защищает от интерпретации текста как HTML. В проекте нет |safe для отзывов и сообщений пользователя.

Поля форм выводятся через `{{ field }}`. Django сам создаёт id, name, type и текущее значение. `field.errors` выводит ошибки конкретного поля, `form.non_field_errors` — ошибки всей формы. label for связан с id поля, поэтому клик по подписи переводит фокус в нужный input.

## 15. CSS: как получается адаптив

`display:grid` создаёт сетку. `grid-template-columns:1fr 1fr` делит доступную ширину на две равные части. `gap` задаёт расстояние между колонками. `minmax(0,1fr)` разрешает колонке сжиматься, даже если внутри длинный текст.

`box-sizing:border-box` включает padding и border в заданную ширину. Без этого input width:100% плюс внутренние отступы мог бы оказаться шире карточки. `overflow-wrap:anywhere` разрешает перенос длинного email и названия.

@media(max-width:760px) применяется по ширине окна. На телефоне сетка становится одноколоночной, а меню переносится. Макеты mobile/ дополнительно принудительно применяют эти правила, чтобы оставаться холстом 390 px даже в большом окне компьютера.

CSS-переменные --teal и --ink задаются в :root. `var(--teal)` подставляет значение. Так цвет кнопок и ссылок можно изменить в одном месте. :focus-visible рисует заметную рамку для клавиатурной навигации. prefers-reduced-motion отключает анимации по настройке пользователя.

## 16. JavaScript: почему слайдер зациклен

Массив из четырёх кадров имеет индексы 0,1,2,3. Чтобы показать предыдущий с нуля, нужно получить 3, а не -1. Поэтому используется `(nextIndex + slides.length) % slides.length`. Для следующего с тройки получаем `(4+4)%4=0`. Остаток от деления замыкает цикл.

`const` запрещает переназначить ссылку переменной, `let` допускает изменение. index меняется, поэтому let. slides остаётся тем же массивом, поэтому const. Стрелочная функция `() => show(index+1)` передаёт действие, которое выполнится позднее при событии.

classList.toggle("active", active) добавляет или снимает класс по логическому условию. CSS делает активный кадр непрозрачным. setInterval получает функцию и 3000 миллисекунд. clearInterval останавливает повторение. Перед запуском нового таймера старый удаляется, иначе карусель могла бы неожиданно ускоряться.

Индикатор формы появляется при submit после стандартной валидации браузера. Повторная кнопка отключается. На pageshow она включается обратно, потому что браузер может вернуть старую страницу из кэша кнопкой «Назад». Основная логика заявки работает на сервере и не зависит от JavaScript.

## 17. Тесты и их границы

TestCase использует отдельную тестовую БД и откатывает данные между тестами. Client вызывает обработчики Django без настоящего браузера. Проверяются серверные ответы, права и фактические записи. Это не визуальная проверка CSS.

Слайдер проверяется отдельным Node-скриптом с минимальной моделью DOM: переходы, активный кадр, aria-hidden, таймер, пауза и отправка формы. Такой тест тоже не доказывает, что в браузере правильно отрисовались отступы.

В этой среде настоящий Chromium не стартовал из-за системного ограничения создания Unix-сокета. Поэтому на своём компьютере выполните ручную визуальную проверку пяти страниц и размера 390×844 по CHECKLIST. Не заменяйте это утверждением «все браузеры проверены».
