Учимся писать «Корочки.есть» на Django

Твоя цель — самостоятельно написать работу. Поэтому читай не весь проект подряд, а проходи один понятный шаг за другим: данные → проверка → действие → адрес → HTML. Затем повторяй шаг без готового файла перед глазами.

Для чтения ничего устанавливать не нужно. В самом коде справа от каждой непустой строки стоит объяснение. Здесь разбираются общие принципы, чтобы комментарии не превращались в набор слов, который приходится заучивать.

1. Сначала пойми одну цепочку

Человек открывает адрес → Django выбирает функцию → функция получает данные → проверяет их → читает или изменяет БД → возвращает HTML или перенаправление.

На примере заявки:

  1. Открыт /applications/new/ — это GET-запрос, человек ещё ничего не отправил.
  2. В portal/urls.py этот путь связан с new_application_view.
  3. Функция создаёт пустую ApplicationForm и показывает её в HTML.
  4. Человек выбирает курс, вводит дату и нажимает «Отправить заявку».
  5. Браузер посылает POST на тот же адрес.
  6. Функция связывает форму с request.POST и вызывает is_valid().
  7. Если ошибок нет, создаёт объект, назначает владельца и сохраняет в БД.
  8. redirect("applications") направляет браузер к списку.
  9. Список выбирает только записи этого пользователя и показывает их.

Пока не можешь пересказать эту цепочку, не переходи к слайдеру и красивому оформлению.

2. Порядок написания с нуля

Шаг 1. Каркас и настройки

При самостоятельной тренировке создаются проект config и приложение portal. В уже скачанном Demo создавать их повторно не надо.

# Создать проект в текущей папке; точка в конце означает именно текущую папку.
python -m django startproject config .
# Создать приложение с нашими моделями и страницами.
python manage.py startapp portal

В settings.py добавь portal в INSTALLED_APPS, укажи папку templates, статические файлы и SQLite. AUTH_USER_MODEL = "portal.User" нужно указать до первого migrate, потому что проект использует свою модель пользователя.

Настройки не нужно переписывать наугад: стандартный startproject уже создаёт большую часть. В нашем settings.py каждой строке дано пояснение. Случайный локальный ключ хранится в .local_secret и не отправляется в Git.

Шаг 2. Модели — какие данные храним

Открой portal/models.py.

  • User — обычный пользователь Django плюс ФИО и телефон. Логин, пароль, email и is_staff уже получены от AbstractUser.
  • Course — название курса.
  • Application — владелец, курс, дата, оплата, статус и отзыв.

class User(AbstractUser) означает: «Возьми готовые возможности пользователя и добавь мои поля». Это наследование и пример ООП. Не нужно отдельно писать таблицу паролей, собственный алгоритм хеша и всю систему входа.

CharField — короткая строка. TextField — большой текст. DateField — настоящая дата. ForeignKey — ссылка на другую таблицу.

user = ForeignKey(User, ...) не копирует целого пользователя в каждую заявку. В БД появляется число user_id. Django по этому числу может получить связанный объект: item.user.full_name.

on_delete=PROTECT запрещает удалить пользователя или курс, пока на него ссылается заявка. Так история не потеряется случайно.

choices=STATUSES даёт форме допустимые варианты. В коде используются короткие значения new/studying/completed, а на сайте показываются русские подписи. default="new" назначает начальный статус новой записи.

blank=True разрешает пустой отзыв при создании заявки. default="" означает, что сначала он хранится пустой строкой.

class Meta с ordering=["-id"] означает: при обычном выборе сортировать записи от большого id к маленькому — новые раньше старых.

После моделей:

# Создать файл изменения структуры БД по написанным моделям.
python manage.py makemigrations
# Выполнить изменения и создать таблицы.
python manage.py migrate

Проверка себя: можешь ли ты нарисовать три прямоугольника User, Course, Application и показать две связи один-ко-многим? Если да, модель понятна.

Шаг 3. Формы — какие данные принимаем

Открой portal/forms.py. Здесь четыре небольших класса.

Форма Для чего
RegisterForm Создать пользователя с правильными полями и паролем
ApplicationForm Принять только курс, дату и оплату
ReviewForm Принять только текст отзыва
StatusForm Принять только один разрешённый статус

ModelForm — форма, связанная с моделью. Её Meta.model указывает таблицу, Meta.fields перечисляет поля, которые посетитель имеет право отправлять.

Почему в ApplicationForm нет user и status? Потому что эти значения нельзя доверять браузеру. Владелец берётся из входа в аккаунт, статус новой записи — из модели.

RegisterForm наследует UserCreationForm. Родитель уже сравнивает password1/password2 и сохраняет хеш пароля. Мы добавляем нужные поля и правила. Дополнительный повтор пароля помогает поймать опечатку.

RegexField проверяет текст по регулярному выражению. EmailField проверяет email. PasswordInput скрывает ввод. Textarea создаёт большое поле. RadioSelect показывает варианты оплаты кружочками.

widget отвечает за внешний HTML, а поле формы — за проверку на сервере. Поэтому есть pattern/minlength в браузере и независимая серверная проверка. Обход браузера не должен давать возможность записать неправильные данные.

Шаг 4. Обычная проверка формы

Разбери эти выражения отдельно:

  • request.method == "POST" — человек отправил форму, а не просто открыл страницу.
  • request.POST — словарь отправленных значений.
  • form.is_valid() — проверить все поля и вернуть True или False.
  • form.cleaned_data — уже проверенные и преобразованные значения; дата здесь является объектом даты, а не сырой строкой.
  • form.save() — сохранить результат, если это ModelForm.

Почему написано request.POST if request.method == "POST" else None? При GET нужна пустая несвязанная форма. При POST нужна связанная форма, которая будет показывать введённое и ошибки. Пустой POST всё равно должен проверяться, поэтому мы явно смотрим метод.

В ApplicationForm метод clean_start_date вызывается после проверки DateField. DateField отвергает несуществующий день, а сравнение со strftime дополнительно требует точную запись ДД.ММ.ГГГГ с нулями. В отличие от старого примера из архива, 31 февраля не проходит.

Прошлые даты в этом учебном варианте отдельно не запрещены: такого ограничения в присланном официальном тексте нет. Если оно будет в другом варианте — добавишь свою проверку.

Шаг 5. View — что сделать при запросе

Открой portal/views.py и начни с applications_view, потому что это самая простая полезная функция.

items = Application.objects.filter(user=request.user)  # Взять только заявки того, кто сейчас вошёл.
return render(request, "portal/applications.html", {"items": items})  # Показать HTML и передать ему найденный список.

Application.objects — менеджер работы с таблицей. filter задаёт условие выборки. request.user — пользователь, которого Django определил по сессии. Словарь {"items": items} даёт шаблону имя переменной.

Дальше читай new_application_view:

item = form.save(commit=False)  # Получить объект в памяти, пока без записи в БД.
item.user = request.user  # Назначить владельца со стороны сервера.
item.save()  # Сохранить заполненную заявку.

Почему не просто form.save? В форме намеренно нет поля user. Если сохранить слишком рано, заявке не будет назначен обязательный владелец. commit=False позволяет его дописать.

Отдельного item.status = "new" не нужно: модель уже задаёт default. Если посетитель добавит status=completed в POST, ModelForm проигнорирует это поле, поскольку его нет в Meta.fields.

После записи используется redirect. Обновляя список, браузер повторит GET, а не предыдущий POST. Это обычный приём POST → Redirect → GET. Он не запрещает две намеренно отдельно отправленные заявки, но предотвращает обычное повторение формы кнопкой обновления страницы.

Шаг 6. Адреса

В portal/urls.py каждая строка отвечает на вопрос: «Какую функцию вызвать для этого пути?»

path("applications/new/", views.new_application_view, name="new_application") содержит:

  • путь от корня сайта;
  • функцию, которая будет вызвана;
  • короткое имя адреса для ссылок и redirect.

В шаблоне {% url 'new_application' %} найдёт тот же маршрут по имени. Если изменится путь, не придётся вручную искать все ссылки по проекту.

<int:pk> означает числовую часть адреса. В /applications/17/review/ функция получит pk=17. Само знание числа не даёт права на запись: view дополнительно проверяет владельца.

В config/urls.py include подключает все адреса приложения portal.

Шаг 7. HTML

Начни с templates/base.html. Это общая оболочка: head, шапка, меню, main, подвал. {% block content %} — место для содержимого конкретной страницы.

{% extends "base.html" %} берёт оболочку. {{ value }} выводит значение. {% if %} выбирает ветку. {% for %} перебирает записи. {% empty %} выполняется, когда список пустой.

В form.html один простой цикл показывает поля любой из наших форм. {{ field }} создаёт готовый input/select/textarea. {{ field.errors }} показывает ошибку рядом с полем. {{ form.non_field_errors }} показывает общую ошибку — например, неправильный логин/пароль.

method="post" отправляет поля в request.POST. Атрибут name становится именем отправленного значения. {% csrf_token %} добавляет защитное скрытое поле. Не удаляй его ради уменьшения числа строк.

{{ item.get_status_display }} выводит русскую подпись choices. {{ item.start_date|date:"d.m.Y" }} отображает дату привычно человеку.

Django экранирует пользовательский текст. Поэтому <script> в отзыве станет буквальным текстом. Не добавляй |safe к отзывам, чтобы случайно не отключить эту защиту.

Шаг 8. Регистрация и вход

В register_view форма проверяется и сохраняется, затем человек переходит на вход. Хеш создаёт UserCreationForm, а не наше присваивание password.

В login_view используется готовая AuthenticationForm. form.get_user() возвращает найденного пользователя. login(request, user) создаёт сессию. На следующих запросах Django определяет request.user по сессии.

У Admin пять букв, а обычный новый логин должен иметь минимум шесть. Поэтому проверка длины находится в регистрации, а форма входа принимает существующего Admin. Пароль администратора при создании вводится по условию задания и не находится в публичном исходнике.

is_staff — флаг роли из БД. Если он True, открывается /admin/. Если False — /applications/. Значение не берётся из POST регистрации.

Шаг 9. Защита страниц

@login_required над функцией проверяет вход до выполнения её тела. Гость будет отправлен на login.

@require_POST не позволяет изменять данные обычным открытием GET-ссылки. В проекте так защищены выход, отзыв и статус.

В административной панели и в отдельном status_view есть проверка if not request.user.is_staff. Нужны обе: посетитель может не открывать страницу, а попробовать сразу отправить POST на адрес изменения.

Отзыв получает заявку через get_object_or_404(Application, pk=pk, user=request.user). Обрати внимание на последнее условие. Без него можно было бы указать номер чужой заявки. С ним чужая запись не находится и возвращается 404.

После этого view проверяет item.status == "completed". Скрыть форму в HTML недостаточно: злоумышленник может отправить запрос вручную.

Шаг 10. Статус, фильтр и страницы

StatusForm — самая простая форма: один ChoiceField со списком STATUSES. is_valid отвергает неизвестный код. После проверки статус сохраняется обычными присваиванием и save.

В официальном тексте администратор после просмотра может выбрать «Идет обучение» или «Обучение завершено». Поэтому мы не добавляем лишнюю цепочку запретов: любой известный статус допустим для администратора.

Фильтр приходит через GET: /admin/?status=new. request.GET.get("status", "") возвращает выбранное значение или пустую строку. ORM подставляет значение безопасным параметром. Неизвестный статус даст пустой результат, а не SQL-ошибку.

Paginator(items, 5) делит выборку на пятёрки. get_page выбирает страницу и безопасно обрабатывает некорректный номер. В шаблоне ссылки «Назад» и «Далее» сохраняют status в адресе.

messages.success сохраняет подтверждение до следующей страницы. base.html выводит его после redirect.

Шаг 11. CSS и слайдер — после работающей логики

CSS здесь простой: общий фон, карточка, поля, кнопки и мобильная перестройка шапки. Всё лежит в одном коротком файле.

box-sizing:border-box включает внутренние отступы и рамку в ширину. width:100% тогда не выталкивает поле за карточку. max-width ограничивает форму на компьютере. @media уменьшает отступы и переносит меню на телефоне.

Четыре фотографии из присланного приложения приведены к одному размеру 800×450. В slider.html ровно четыре img. Кадр с классом active виден, остальные прозрачны.

В JS номер кадра начинается с нуля. Формула (number + slides.length) % slides.length делает переключение циклическим. С четвертого вперёд попадём на первый, с первого назад — на четвёртый. setInterval с 3000 запускает шаг раз в три секунды. Если в системе включено ограничение движения, автосмена отключается, а кнопки остаются.

Надпись кнопки меняется на «Сохраняем…» при отправке. pageshow восстанавливает её после возврата назад. Основная логика на сервере работает и при отключённом JavaScript.

4. Регулярки без заучивания всей строки

Логин: \A[A-Za-z0-9]{6,50}\Z.

  • \A и \Z — начало и конец всей строки.
  • Квадратные скобки задают один допустимый символ.
  • A-Z и a-z — латинские буквы, 0-9 — цифры.
  • {6,50} — длина от шести до пятидесяти.

Телефон: 8\([0-9]{3}\)[0-9]{3}-[0-9]{2}-[0-9]{2}.

  • 8, скобки и дефисы должны присутствовать буквально.
  • Обратный слеш перед скобкой говорит: «Это символ скобки, не группа».
  • {3} означает ровно три цифры, {2} — две.

ФИО: кириллическое слово, затем сколько угодно повторений «пробел + слово». Ё/ё добавлены отдельно. Пустое имя и латиница не подходят. Дефис не разрешён, потому что выбранное правило задания допускает кириллицу и пробелы.

В raw-строке r"..." Python не обрабатывает обратные слеши раньше регулярного выражения. Поэтому их проще читать.

5. Как тренироваться

Не переписывай сразу весь готовый файл. Сделай маленькую часть, запусти её при возможности, объясни её вслух, затем закрой образец и напиши снова.

Сначала достаточно уметь самостоятельно написать модель Course и вывести её список. Затем добавь модель Application и пустую форму. Потом сделай POST, проверку и сохранение. Только после этого подключай владельца, вход, отзыв и админку.

Критерий понимания простой: ты можешь изменить требование, а не только повторить строки. Например, добавить комментарий к заявке и объяснить, какие файлы придётся изменить. Такие упражнения есть в PRAKTIKA.md.

Миграции и тесты не учи первыми. Миграции генерирует Django, а тесты помогают проверить уже написанное. Читай текущие models/forms/views/templates, а не старую историю изменения схемы.

Практика: от маленького примера к самостоятельной работе

Работай в отдельной тренировочной папке или ветке, чтобы можно было сравнивать с образцом. Сначала попробуй решить без подглядывания, затем сверяйся. Если читаешь без компьютера, записывай ответ на бумаге и объясняй, что попадёт в каждую переменную.

1. Модели

  1. Напиши Course с одним полем title. Объясни max_length и unique.
  2. Добавь str. Предскажи, что изменится в выпадающем списке.
  3. Напиши Application с course, user и start_date. Нарисуй связи.
  4. Добавь статус с default new. Почему форму не нужно просить прислать начальный статус?
  5. Не глядя в образец, напиши две команды создания и применения миграции.

2. Форма и сохранение

  1. Напиши ModelForm, принимающую только курс и дату. Почему user не включён?
  2. Напиши view: GET → пустая форма; POST → проверка. Сначала просто покажи данные, потом добавь сохранение.
  3. Добавь commit=False и владельца из request.user. Объясни, в какой момент объект попадает в БД.
  4. Сделай redirect после сохранения. Что произойдёт при обновлении следующей страницы?
  5. Выведи ошибки под полями, а не одним общим сообщением сверху.

3. Личный кабинет

  1. Выведи только заявки вошедшего пользователя. Почему objects.all здесь неправильно?
